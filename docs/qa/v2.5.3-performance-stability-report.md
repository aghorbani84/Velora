## Executive verdict

The v2.5.3 release pipeline is healthy: signing, certificate verification, Detekt, the selected unit/domain suites, release APK assembly, packaging and GitHub publication all passed. A real Android Emulator run also completed successfully and produced a raw logcat artifact.

Memory, CPU and process-start measurements are now available for one controlled emulator sample. This is not yet a complete performance certificate: the run did not play audio, exercise the visualizer deliberately, scroll large libraries, measure frame/jank or measure battery drain, and it used one emulator configuration and one sample window.

Therefore:

- **Release/build stability:** PASS.
- **Repository/domain regression gates:** PASS for the CI-selected suites.
- **Room indexing micro-benchmark:** IMPLEMENTED in source, but not executed by the v2.5.3 release workflow.
- **Runtime memory:** MEASURED once on emulator; requires baseline and repeated runs.
- **Runtime CPU:** MEASURED once during a nominal idle sample; result is high enough to investigate.
- **Process startup:** MEASURED as process-start latency; first-frame startup was not measured.
- **Frame/jank/battery:** NOT MEASURED.
- **Overall runtime performance acceptance:** PARTIALLY TESTED; not complete.

## Automated test coverage relevant to stability

The repository contains domain and Robolectric coverage for playback orchestration, queue/settings persistence, DSP mathematics, secure download validation, fullscreen policy and a missing-file error state. These are valuable regression gates, but they do not prove long-running device stability or resource efficiency.

The v2.5.3 release workflow explicitly runs:

```text
com.example.ExampleUnitTest
com.example.DspBiquadMathTest
com.example.DownloadValidatorSecurityTest
com.example.FullscreenPolicyTest
```

The source-level Room micro-benchmark is:

```text
100 TrackEntity insertions + one query < 500 ms
```

Its assertion is meaningful only when that test is actually executed on a known environment. It should not be reported as a measured v2.5.3 release result until the CI command includes it and the test output is retained.

## Real emulator measurements

**Workflow:** [43694056782](https://github.com/aghorbani84/Velora/actions/runs/43694056782)  
**Runner:** GitHub-hosted `ubuntu-latest`  
**Emulator:** Android API 34, x86_64, Pixel 2 profile, software GPU  
**Test:** `PerformanceInstrumentedTest.captureColdStartMemoryAndCpuOnEmulator`

| Metric | Measured result | Measurement definition |
|---|---:|---|
| Process start latency | **910 ms** | From `startActivity()` until the target app process PID became visible. This is not first-frame time. |
| Target process PSS | **185,284 KB / 180.94 MiB** | `ActivityManager.getProcessMemoryInfo()` after process start plus a 5-second settle period. |
| CPU utilization | **57.91%** | Target process CPU ticks sampled for approximately 5.958 seconds after the settle period. |
| Sample window | **5,958 ms** | Actual elapsed sample window. |
| Device/API | **Android SDK built for x86_64 / API 34** | Emulator configuration recorded by the instrumentation log. |

### Interpretation

The measured PSS is approximately **181 MiB** in the tested post-start state. The measured CPU utilization of **57.91%** during the nominal sample is materially higher than an expected idle-playback baseline and should be investigated, especially around Compose/visualizer recomposition, Media3 initialization, Firebase/Koin startup work and any continuous animation. It is not a proof of sustained production-device CPU usage because it is a single emulator sample and no audio track was playing.

The instrumentation used process-level PSS and `/proc/<pid>/stat` CPU ticks; it is a lightweight measurement, not a replacement for Android Studio Profiler or Perfetto. The raw logcat and summary were uploaded in the `VELORA-v2.5.3-emulator-performance` artifact attached to workflow 43694056782.

## Missing performance evidence

No reproducible v2.5.3 evidence is available yet for:

1. Peak/steady-state Java/Kotlin heap or native RSS during Home, Library, Now Playing, artwork loading, queue scrolling and Studio/DSP use. The single PSS sample above is not a peak profile.
2. CPU utilization or thread CPU time during actual audio playback, decode, visualizer updates, EQ changes and rapid queue transitions.
3. Cold/warm startup time to first frame and first interactive frame. The current 910 ms value is process-start latency only.
4. Frame time, jank percentage or dropped frames on compact and tablet configurations.
5. Battery/power drain during a defined playback soak.
6. A long-running playback soak with repeated next/previous, seek, pause/resume and route changes.
7. Performance behavior under large libraries, large font scale, Persian RTL and low-memory pressure.

## Risk interpretation

There is no evidence here of a release-blocking build or test regression. However, absence of measurements is not evidence of low resource usage. The most relevant areas requiring device measurement are the real-time visualizer, artwork loading/Coil cache behavior, Media3 lifecycle during repeated transitions, Room library scans and the 10-band DSP path.

The KSP AWT null-pointer messages visible as CI annotations occurred during the successful build and did not fail the job. They are build-tool warnings/noise to monitor, not a measured app runtime fault.

## Acceptance recommendation

Keep v2.5.3 marked **release/build verified** and **partially performance-measured**, but do not mark full runtime performance acceptance complete until additional scenarios produce:

- Android Studio Profiler or Perfetto traces for memory and CPU, in addition to the lightweight sample now recorded.
- Macrobenchmark or equivalent startup/frame measurements.
- A documented playback soak test with duration, device/API, media format and actions.
- Captured results attached to the CI run or QA report.
